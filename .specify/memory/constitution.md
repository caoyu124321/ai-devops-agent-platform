# AI DevOps 智能体平台章程

## 目的

本章程规定如何使用规范驱动开发（Spec-Driven Development，SDD）来开发本仓库。在接受功能规范、实施计划、任务清单或代码变更之前，均以本章程作为稳定的决策框架。

## 原则

### I. 先规范，后实现

每项产品变更都必须始于功能规范，其中应说明用户价值、验收场景、功能需求和可衡量的成功标准。架构、框架选型、数据库模式和实施任务不得作为需求处理。

在规范通过需求检查清单，且所有阻塞性歧义均已解决或明确推迟处理之前，不得开始编写生产代码。

### II. 交付精简且可独立测试的功能切片

功能必须以能够为用户提供可感知价值的最小端到端切片进行交付。切片应根据实际情况包含 API 或 UI 契约、授权、错误处理行为、测试和运维信号。

在具体用户故事提出要求之前，平台不得引入通用扩展点、分布式组件或集成。

### III. 安全执行是一项产品需求

流水线执行、部署、凭据、源代码管理 Webhook 和插件均属于安全敏感领域。任何能够执行工作或暴露数据的功能，都必须在其规范中定义授权、失败行为、取消或超时行为，以及秘密信息处理约束。

凭据必须通过引用使用，不得以明文形式存储或记录在日志中。执行过程必须遵循最小权限原则，并在隔离且受策略控制的环境中进行。

### IV. 行为必须可观测且可恢复

每个异步操作都必须公开稳定的标识、生命周期状态、时间戳和可操作的失败信息。长时间运行的工作必须定义超时、取消语义和重试语义。

日志和运维事件必须能够关联到触发它们的、用户可见的流水线运行及步骤运行。

### V. 由测试证明满足验收标准

规范中的每个验收场景都必须在具有实际意义的最低测试层级上由自动化测试覆盖。集成边界（存储、队列、插件、外部服务）需要契约测试或集成测试。如果无法验证功能声明的成功标准，则该功能尚未完成。

### VI. 决策必须明确，并尽可能可逆

未知的产品决策应记录为待澄清事项，不得在未说明的情况下自行假设。技术决策应归入实施计划，并且必须能够追溯到具体需求。对于逆转成本较高的决策，必须提供一份简短的决策记录，说明备选方案及其后果。

### VII. 代码规范

1.代码中的业务逻辑必须添加清晰、准确的中文注释，用于说明业务意图、关键规则和必要的边界条件。注释应解释代码为何这样实现，不得仅对代码行为进行机械复述；代码变更后，相关注释必须同步更新。
2.方法和方法之间要空行，方法内部不需要空行，按照alibaba代码规范
3.Controller层不得有业务逻辑，业务逻辑统一放到Service层，数据库操作放在Dao层
4.try-catch不得直接抛出Exception，需要自定义有业务属性的异常
5.在代码中需要添加关键日志，方便问题定位，但不得打印敏感信息，如密码、ak、sk
6.代码实现完成后，必须依据对应的用户故事（User Story）及其验收场景编写单元测试。测试必须覆盖主要业务流程、关键边界条件和预期失败场景。只有在相关单元测试全部执行通过，并对测试结果完成检查后，代码任务才可视为完成。

### VIII. 技术选型
1.项目架构应为 springboot全家桶+mybatis

## 必需的 SDD 生命周期

1. **章程（Constitution）** — 确立不可妥协的项目原则。
2. **规范（Specify）** — 创建 `specs/<feature>/spec.md`；编写用户故事、验收场景、需求、成功标准和待解决问题。
3. **检查与澄清（Check and clarify）** — 使用 `checklists/requirements.md`；在不向规范中添加技术设计的前提下解决阻塞问题。
4. **计划（Plan）** — 仅在规范获准后创建 `plan.md`；记录架构、数据模型、契约、调研结果和风险决策。
5. **任务（Task）** — 创建 `tasks.md`；将获准的计划拆分为有序且可独立验证的工作项。
6. **实现（Implement）** — 每次进行一项任务规模的变更，并持续更新测试和文档。
7. **验证与评审（Verify and review）** — 演示每个验收场景、更新可追溯关系，并单独记录后续工作。

## 仓库约定

- 实现方案、接口定义等信息都在 `.specify/<module_name>` 目录下
- 项目采用多模块的结构
- `spec.md` 面向产品，且与具体实现无关。
- `plan.md`、`research.md`、`data-model.md`、`contracts/` 和 `quickstart.md` 仅在计划阶段创建。
- `tasks.md` 仅在计划获准后创建。
- 需求标识符使用 `FR-xxx`；用户故事使用 `USx`；验收场景使用 `AS-x.y`。
- 对已接受规范的任何变更都必须递增其修订版本，并重新执行需求检查清单。

## 治理

本章程的效力高于临时性的实现偏好。如需偏离本章程，必须在相关计划中记录原因、影响和批准情况。修改本章程时，必须检查所有进行中的规范是否存在冲突。
