# 流水线模块规格

**修订版本**：0.1  
**状态**：需求检查通过，可进入技术设计。  
**关联文档**：[模块说明](README.md) · [待确认事项](open-questions.md) · [模块 TODO](../module-todo.md)

## 用户价值

开发者和项目管理员可在项目内保存、校验和运行受控 YAML 流水线。用户只需要选择明确的项目、代码版本和环境；平台通过 IAM、项目预配置和插件契约拒绝无权限、未配置或不可执行的请求。具体构建、测试和部署任务能够独立以插件演进，不会使流水线核心依赖某一种构建工具或部署平台。

## 用户故事与验收场景

### US-PL-01 创建并维护流水线

作为项目管理员，我希望在项目内创建、修改、启用或停用 YAML 流水线，以便团队复用经过校验的交付流程。

- AS-PL-01.1：有项目范围流水线编辑权限的用户可保存合法 YAML；每次有效保存产生新的不可变版本。
- AS-PL-01.2：停用流水线后不得创建新运行，历史版本和历史运行仍可查询。
- AS-PL-01.3：用户只能管理自己有权限的项目流水线；跨租户或无权限流水线不可见。
- AS-PL-01.4：后续编辑、停用或删除不改变历史版本及其已创建运行的语义。

### US-PL-02 校验 YAML 和引用资源

作为流水线编写者，我希望在执行前获得可定位的校验结果，以便修复 YAML、资源或权限问题。

- AS-PL-02.1：YAML 语法、必填字段、参数类型、变量引用、插件输入和步骤依赖均被校验。
- AS-PL-02.2：循环依赖、未知或已停用插件、无权限插件、跨项目仓库/环境和不健康环境均被拒绝。
- AS-PL-02.3：校验错误必须包含路径、行列、规则编号、原因和修复建议，且不得含敏感信息。

### US-PL-03 创建一次运行

作为开发者，我希望针对明确的流水线版本、代码分支或提交和环境创建运行，以便交付项目变更。

- AS-PL-03.1：创建运行时必须指定项目和已启用流水线版本；代码源、分支/提交、目标环境及运行参数遵循已确认的覆盖规则。
- AS-PL-03.2：系统在创建时复查用户的流水线运行、仓库使用和环境部署权限，并固定流水线、插件和预配置资源快照。
- AS-PL-03.3：重复提交相同幂等键只产生一个运行；无权限、未配置或不健康资源不得产生可执行运行。

### US-PL-04 跟踪、取消和重试运行

作为运行发起人或有权限的项目成员，我希望查询运行过程并在必要时取消或重试，以便处理交付失败。

- AS-PL-04.1：运行、阶段、步骤公开稳定标识、状态、时间戳、失败原因和日志引用。
- AS-PL-04.2：失败、取消或超时后，不满足依赖条件的后续步骤必须跳过，不得继续执行。
- AS-PL-04.3：取消语义按插件执行类型生效；运行终态后不得被继续调度。
- AS-PL-04.4：重试使用原始流水线、插件与配置快照，并重新进行执行前授权复查。

### US-PL-05 通过插件执行任务

作为平台能力提供者，我希望独立注册受控插件，以便增加构建、测试或部署能力而无需修改流水线核心。

- AS-PL-05.1：流水线只能引用已注册、已启用且版本明确的插件描述符。
- AS-PL-05.2：调度器仅依据插件通用执行契约调用任务、接收状态/日志/输出/产物引用；不得根据 Maven、Docker 或 Kubernetes 名称分支处理业务逻辑。
- AS-PL-05.3：插件停用不会篡改历史运行；新运行引用停用插件时被拒绝。

### US-PL-06 安全地执行 Docker 和部署任务

作为租户管理员，我希望流水线只在受控边界内执行任务，以便保护宿主机、凭据和部署环境。

- AS-PL-06.1：Docker 类型插件禁止特权模式、Docker Socket、任意宿主机挂载和未经声明的镜像。
- AS-PL-06.2：Kubernetes 插件只能使用当前项目已授权、启用且健康的环境和允许命名空间；凭据只能通过受控引用使用。
- AS-PL-06.3：日志、错误、API 响应和给 MCP/LLM 的上下文均不包含密码、Token、私钥、Kubeconfig 原文或其他敏感值。

## 功能需求

- FR-PL-001：所有流水线、版本、运行、阶段、步骤、日志和产物必须归属单一项目并受租户隔离。
- FR-PL-002：流水线核心必须与具体任务解耦；核心只依赖插件描述符和通用执行结果，不能内置构建、Docker 或 Kubernetes 任务逻辑。
- FR-PL-003：流水线 YAML 必须声明版本化的步骤依赖和插件引用；不得嵌入凭据、任意命令或绕过预配置资源的连接信息。
- FR-PL-004：流水线版本、插件版本、仓库、环境与凭据引用版本必须在运行创建时固定；历史运行不受后续配置修改影响。
- FR-PL-005：保存和执行前必须校验 YAML、引用资源、插件、权限和环境可用性；执行前还须进行当前权限复查。
- FR-PL-006：运行、阶段和步骤必须具有明确状态机、状态时间戳、失败/取消/超时语义、依赖传播和可查询日志。
- FR-PL-007：调用方指定幂等键时，重复运行创建请求必须返回同一运行，不得重复调度。
- FR-PL-008：Docker 插件和 Kubernetes 插件必须遵守产品定义中的最小权限、隔离和凭据脱敏边界。
- FR-PL-009：插件描述符应定义名称、版本、执行类型、输入/输出、所需授权、超时和支持的目标类型；插件版本或停用状态的变化不得改变历史运行。
- FR-PL-010：MVP 仅支持手动触发、公开 GitHub HTTPS 仓库、Maven/Java 构建与测试、以及 Kubernetes 部署；其他触发方式、部署平台和任意脚本均不在范围内。
- FR-PL-011：REST/MCP 接口只执行统一授权后的受控操作；用户未明确选择项目、代码版本或环境时，接口必须要求补充信息而非猜测。

## 成功标准

- 合法 YAML 可被保存为不可变版本，非法 YAML 能在执行前被清晰拒绝。
- 运行可完整追溯到流水线、插件及预配置资源快照；失败、取消和超时不会继续执行不符合依赖条件的步骤。
- 增加新的插件类型不需要修改流水线核心的任务调度规则。
- 无权限用户不能跨项目读取、运行、取消或部署；敏感信息不出现在对外输出中。

## 非范围

本阶段不在规格中确定数据库表、ORM、Controller、Service、线程/队列模型、Docker SDK、Kubernetes SDK、产物存储实现或 MCP 工具实现细节；这些内容只在规格获得确认后进入技术设计。
