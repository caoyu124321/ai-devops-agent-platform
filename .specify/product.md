# 产品定义：AI DevOps Assistant

**版本**：0.2（已确认）
**状态**：可进入功能规格拆分
**更新时间**：2026-07-17

## 1. 产品简介

AI DevOps Assistant 是一个面向开发团队的智能 DevOps 平台。它让开发者以自然语言表达交付意图，例如“部署 `main` 分支到测试环境”，由 LLM 将意图拆解为构建、测试、部署等受控步骤，再通过 MCP 调用平台能力创建、校验和执行流水线。

产品的目标不是替代所有 CI/CD 工具，而是降低使用门槛：开发者关注代码和交付目标，平台负责生成受控的执行方案、调用已授权的环境和凭据、展示执行过程，并在失败后辅助定位原因。

## 2. 背景与问题

当前软件交付流程常见以下问题：

1. **流水线配置复杂**：开发者需要理解并手写 YAML，配置容易重复、出错且难以统一。
2. **部署知识门槛高**：完成一次部署往往需要掌握 Docker、Kubernetes、Helm、服务器连接和环境变量等知识。
3. **环境信息分散**：代码仓库、部署机器、凭据、镜像地址和运行参数分散在不同工具或个人电脑中。
4. **失败定位困难**：构建或部署失败后，用户必须人工阅读大量日志、猜测原因、修改参数并再次尝试。
5. **权限控制不足**：传统脚本容易绕过环境权限，导致部署边界难以统一管理。

### 2.1 现有方案的不足

传统 CI/CD 平台通常要求用户自行完成：

- 编写和维护流水线配置；
- 配置构建与部署参数；
- 阅读日志、调试失败并反复修改；
- 管理环境、凭据和部署权限。

AI DevOps Assistant 在保留声明式流水线的前提下，增加自然语言交互、智能建议、自动诊断和受控执行能力。

## 3. 目标用户

| 用户 | 主要诉求 |
| --- | --- |
| 开发者 | 用自然语言发起构建、测试、部署；快速理解失败原因 |
| 项目管理员 | 配置项目、Git 仓库、流水线模板、部署环境和成员权限 |
| 平台管理员 | 管理用户、角色、插件和全局安全策略 |
| 观察者 | 查询运行状态、日志、产物和部署历史，但不执行变更 |

## 4. 产品目标

### G1：通过自然语言生成并执行流水线

用户输入：

> 部署 main 分支到测试环境

系统应完成以下流程：

1. LLM 识别用户意图，拆解为获取源码、构建、测试和部署等步骤。
2. LLM 通过 MCP 调用本平台的能力，查询用户可访问的项目、仓库和部署环境。
3. 平台根据用户预先配置的 Git 仓库、环境和凭据引用生成候选流水线。
4. 用户或环境策略确认后，平台校验流水线、创建运行并在受控环境中执行。
5. 平台持续返回运行状态、步骤日志、产物和部署结果。

首个 LLM/MCP 接入方为 Codex。用户未登录或身份失效时，MCP 必须返回明确的登录提示；LLM 不得猜测用户身份、环境、凭据或权限。

### G2：自动分析构建与部署失败

当构建、测试或部署失败时，系统应：

1. 收集对应步骤的已脱敏日志、错误码、执行上下文和历史结果。
2. 判断失败类别，例如依赖下载失败、编译失败、测试失败、镜像构建失败、网络/SSH 连接失败、部署配置错误或权限不足。
3. 由 Codex LLM 生成简明的失败摘要、可能原因、证据位置和下一步建议；后续可将失败分析能力以 MCP 工具形式提供给其他客户端。
4. 明确区分“事实日志”与“模型推断”，不得将推断描述为已经确认的事实。
5. 在用户授权范围内提供重试、修改参数后重试或查看详细日志的下一步动作。

### G3：统一管理项目与部署环境

项目管理员可以维护项目、GitHub 仓库地址、部署机器环境、环境状态和成员角色。执行时只能选择当前项目下已启用、调用者有权限使用的环境。

### G4：通过插件扩展交付能力

构建、测试、部署、通知、代码托管和制品管理能力以插件提供。MVP 先支持 Maven/Java 构建、测试和 Kubernetes 部署，后续可扩展 Node.js、Python、Helm、GitLab、Gitee 和通知渠道，而无需改变平台核心流程。

## 5. 关键用户流程

### 5.1 首次配置

1. 平台管理员创建用户并分配角色。
2. 项目管理员创建项目，填写 GitHub 仓库地址。
3. 平台管理员创建 Kubernetes 环境，配置环境等级、集群访问凭据引用、命名空间范围和确认策略。
4. 项目管理员确认可用插件和流水线模板。

### 5.2 自然语言部署

1. 已登录开发者在 LLM 对话中提出交付请求。
2. LLM 经 MCP 查询可用项目和环境；信息不足时向用户提问，而不是自行选择。
3. LLM 生成或选择流水线草案，展示将执行的步骤、仓库、分支和目标环境。
4. 若项目、环境或必要配置不存在，系统要求用户补充或由管理员完成配置；不得创建不完整运行。
5. 若环境策略要求二次确认（例如生产环境），系统展示执行摘要并等待用户明确确认。
6. 满足配置与确认条件后，MCP 调用平台创建运行。
7. 用户通过对话或 REST API 查询进度、日志、产物和最终结果。

### 5.3 失败处理

1. 某一步骤失败、超时或被取消。
2. 平台保存状态和已脱敏日志。
3. 失败分析能力输出原因分类、依据和建议。
4. 用户查看详情后决定修复代码、修改配置、重试或取消后续动作。

## 6. MVP 范围

### 本期包含

- 自定义用户、登录、角色、项目成员和项目级权限。
- GitHub 仓库地址配置；MVP 仅支持公开 GitHub 仓库。
- 由平台管理员管理 Kubernetes 环境的新增、更新、停用、环境等级和确认策略；环境可指向本机、局域网或公网可访问的 Kubernetes 集群。
- YAML 流水线创建、校验、版本保存、手动触发、查询和取消。
- 在受控 Docker 容器中运行 Maven/Java 构建与测试。
- 通过受控 Kubernetes 插件向已配置集群、命名空间执行部署。
- 运行状态、步骤日志、构建产物和部署结果的 REST API。
- MCP 工具：查询上下文、生成/校验流水线、触发运行、查询运行、获取失败分析所需上下文。

### 本期不包含

- 私有 GitHub 仓库、GitHub App、Webhook 自动触发。
- Web 管理界面、SSE/WebSocket 实时日志界面和拖拽式编排。
- Kubernetes、Helm、任意远程 Shell、任意用户上传插件。
- 自动修复代码、自动批准生产部署、多云资源管理和复杂审批流。
- 将凭据明文交给 LLM 或写入流水线 YAML/日志。

## 7. 核心产品规则

1. 所有执行动作必须对应已认证用户、项目、流水线版本和目标环境。
2. LLM 只负责理解、建议和调用受控 MCP 工具；最终执行必须经过平台的权限、参数和安全校验。
3. 用户未明确选择时，系统不得自行决定项目、分支、部署环境或生产操作；项目、环境或必要配置不存在时，必须要求补充信息或管理员配置。
4. 运行引用不可变流水线版本；后续编辑不得改变历史运行语义。
5. 构建与测试在受控 Docker 容器中执行，不允许特权模式、宿主机 Docker Socket 或任意宿主路径挂载。
6. 凭据只以引用形式保存和使用；日志、错误、API 响应和 LLM 上下文必须脱敏。
8. LLM 失败分析必须标注证据与不确定性，用户可跳转到原始日志验证。
9. 每个部署环境必须在创建时设置环境等级（例如开发、测试、预发布、生产）和确认策略；平台管理员决定哪些等级或操作需要用户二次确认。
10. 部署目标可为本机、局域网或公网机器，但只能使用平台管理员已创建、已启用且授权的环境信息。

## 8. 成功指标

| 指标 | MVP 目标 |
| --- | --- |
| 从自然语言请求到创建流水线运行 | 用户可在一次明确交互中完成 |
| 流水线校验反馈 | 2 秒内返回，错误可定位到字段或行列 |
| 运行创建反馈 | 3 秒内返回运行 ID 与初始状态 |
| 日志可见性 | 步骤产生日志后 5 秒内可经 API 查询 |
| 权限安全 | 无权限用户无法读取跨项目数据或触发/部署 |
| 失败分析质量 | 输出失败类别、证据、建议与不确定性说明 |
| 扩展性 | 至少三个内置插件可独立校验和执行 |

## 9. 已确认产品决策

| 编号 | 决策 | 产品影响 |
| --- | --- | --- |
| PQ-001 | 首个 LLM/MCP 接入方为 Codex。 | 平台首先提供面向 Codex 的 MCP 工具和认证交互。 |
| PQ-002 | 项目、环境或必要配置不存在时，不执行并要求补充或配置；部署到需要确认的环境时必须二次确认。 | 避免 LLM 猜测目标或执行不完整流水线。 |
| PQ-003 | 使用 Codex LLM 进行失败分析；后续可将分析能力作为 MCP 工具提供。 | 失败分析结果需包含已脱敏证据、推断和建议。 |
| PQ-004 | 本机、局域网和公网机器均可作为部署目标；部署地址由平台管理员创建的环境信息控制。 | 平台必须按环境配置、网络策略和授权限制连接目标。 |
| PQ-005 | 必须支持环境等级；创建环境时明确等级，不同等级的二次确认策略由平台管理员配置。 | 环境模型需保存等级与确认策略，生产等高风险环境可强制确认。 |
