# 模块 TODO：DevOps 平台 MVP

**范围**：仅需求拆分、模块边界、接口规划和验收顺序。  
**不包含**：表结构、实体设计、技术实现、依赖引入和业务代码。

## 0. 总体模块关系

```text
租户用户模块 ──────────────┐
                           ├─ 项目与预配置模块 ──┐
                           │                       ├─ 流水线模块 ── 运行编排模块
                           │                       │                    │
                           │                       └─ 插件模块 ────────┤
                           └─ 鉴权基础能力 ────────────────────────────┤
                                                                    产物模块
Codex MCP / 智能助手模块 ────────────────────────────────────────────┘
```

“项目”是租户内的隔离边界；仓库、环境、流水线、运行和产物都必须归属一个项目。运行编排负责调度，不与某个具体插件或部署方式耦合。

## 1. 租户用户与权限模块

### 目标

提供平台用户身份、租户成员关系和租户/项目/环境级权限校验，作为其他模块的唯一鉴权入口。

### TODO

- [ ] 定义注册、登录、登出、改密的用户行为与错误场景。
- [ ] 定义租户创建、成员邀请/加入、移除成员、成员角色修改的规则。
- [ ] 定义内置角色：租户管理员、项目管理员、开发者、观察者；明确是否允许自定义角色作为后续能力。
- [ ] 定义权限动作与资源范围：租户管理、项目管理、仓库使用、流水线编辑/运行/取消、产物读取、环境部署。
- [ ] 定义环境等级权限：`DEV`、`TEST`、`STAGING`、`PROD`；权限必须可精确到“某用户是否可部署项目 X 的 PROD 环境 Y”。
- [ ] 为后续二次确认能力预留授权边界；当前 MVP 不实现确认流程或确认接口。
- [ ] 定义认证失效、用户停用、成员移除后对 Token 和运行中任务的影响。

### 验收结果

其他模块仅通过统一授权服务判断“当前用户能否在当前租户/项目/环境执行某动作”，不得各自硬编码角色判断。

## 2. 项目与预配置模块

### 目标

在租户下管理可交付项目、公开 GitHub 仓库、访问凭据引用和项目环境。

### TODO

- [ ] 定义项目创建、启用、停用、成员绑定与项目隔离规则。
- [ ] 定义项目创建、硬删除、项目范围授权初始化和项目隔离规则。
- [ ] 定义公开 GitHub HTTPS 仓库配置：每项目最多 20 个、默认分支、独立新增、只读连通性校验和失效自动删除；不支持私有仓库、SSH URL 或 GitHub Token 访问。
- [ ] 定义凭据引用生命周期：创建、轮换、停用、授权范围；明确凭据值绝不返回给 API、日志或 LLM。
- [ ] 定义三类项目环境：`KUBERNETES`、`LINUX_HOST`、`WINDOWS_HOST`；环境在项目内唯一，支持本机、局域网和公网目标。
- [ ] 定义 Kubernetes 环境配置：集群访问凭据引用、默认命名空间、允许命名空间、`DEV/TEST/STAGING/PROD` 等级、启用状态和只读连通性校验。
- [ ] 定义 Linux SSH 与 Windows HTTPS WinRM 环境配置、主机身份校验、连通性重试和健康状态；当前仅托管配置，不提供主机部署执行。
- [ ] 定义环境权限：租户管理员管理租户内全部环境，项目管理员管理其项目环境；凭据仍仅由租户管理员管理和授权给项目。
- [ ] 定义配置变更对历史运行的影响：运行必须保留启动时使用的配置快照或版本标识。

### 验收结果

任何流水线只能使用所属项目已启用、连接健康且授权的仓库、凭据引用和环境；用户不能跨租户或跨项目引用配置。当前可执行部署仅支持 Kubernetes 环境。

## 3. 流水线定义模块

### 目标

用 YAML 描述可校验、可版本化、可执行的构建、测试、部署流程。

### TODO

- [ ] 定义 YAML v1 顶层字段：名称、描述、参数、代码来源、阶段、步骤、依赖、环境引用、产物声明和变量引用语义；禁止在 YAML 中写入凭据明文。
- [ ] 定义代码来源语义：仓库引用必须属于当前项目；运行时可选择分支或明确提交；用户未指定分支或提交时不得由系统猜测。
- [ ] 定义 `uses: 插件名@版本` 语法及插件输入、输出和参数类型的校验规则；未声明、已停用或不兼容的插件不得保存为可执行版本。
- [ ] 定义 YAML 语法、字段、变量引用、阶段/步骤依赖循环、插件可用性、仓库与环境归属、环境健康状态和权限预校验。
- [ ] 定义流水线创建、查询、更新、启用/停用、版本历史、版本回滚和删除行为；每次有效编辑生成不可变版本。
- [ ] 定义运行参数覆盖规则：允许覆盖代码分支、提交和已声明的运行参数；仓库、凭据引用、项目归属及未声明字段必须来自预配置或流水线版本，不能由运行请求任意指定。
- [ ] 定义无效 YAML 的统一错误格式，必须包含 YAML 路径、行列、规则编号、错误原因和修复建议。
- [ ] 定义流水线版本与运行记录、仓库/环境/凭据配置版本快照的绑定规则，历史运行不得受后续编辑、停用或删除影响。
- [ ] 定义流水线定义 REST 契约：创建、列表、详情、更新、版本列表、版本详情、校验、启停和回滚接口，以及分页、乐观锁与错误响应规则。

### 验收结果

合法 YAML 可保存为不可变版本；无效 YAML 在执行前被拒绝且错误可定位；未知或未授权插件/环境不可引用。

## 4. 运行编排模块

### 目标

创建、调度、跟踪和停止流水线运行；统一处理状态、依赖、超时、取消和日志事件。

### TODO

- [ ] 定义运行、阶段、步骤状态机：排队、运行、成功、失败、取消、超时、跳过；状态转换必须具有时间戳、原因和稳定标识。
- [ ] 定义手动触发输入：项目、流水线版本、Git 分支或提交、目标环境、运行参数；创建前必须复查调用者的项目、流水线、仓库和环境操作权限。
- [ ] 定义运行创建幂等策略：调用方提交幂等键时，重复请求只返回同一运行；未提供幂等键时的重复触发行为也需明确。
- [ ] 定义阶段/步骤依赖、失败传播、跳过和条件执行规则；明确 MVP 是否支持阶段内并行及最大并发数。
- [ ] 定义排队、项目级并发、全局并发、超时和重试策略；重试必须固定原始流水线版本和配置快照。
- [ ] 定义取消规则：未开始步骤、正在执行的进程内插件、Docker 插件和 Kubernetes 部署插件分别如何停止及如何记录最终状态。
- [ ] 定义运行查询、阶段/步骤查询、步骤日志查询、状态变化事件、失败分类和失败摘要的数据契约；日志返回须支持分页或游标。
- [ ] 定义服务重启或 Worker 中断后的运行恢复、重复消费、重复执行防护和人工介入规则。
- [ ] 定义已创建未开始、已开始和长时间运行任务的权限复查时点；权限变更事件由调度模块决定是否停止后续执行。

### 验收结果

一次运行可从创建到终态完整追踪；失败或取消不会继续执行不应执行的依赖步骤；任何状态变化可查询。

## 5. 插件模块

### 目标

将流水线的具体操作封装为可发现、可校验、可调度、可观测的插件。

### TODO

- [ ] 定义插件描述符：名称、版本、类别、执行类型、输入 Schema、输出 Schema、所需权限、超时上限和产物类型。
- [ ] 定义插件注册、启用、停用、版本兼容、升级和历史运行版本固定规则。
- [ ] 定义进程内插件契约：人工卡点、审批、条件判断、通知等；必须支持等待、确认、拒绝、取消和超时。
- [ ] 定义 Docker 插件契约：镜像白名单、工作目录、受控源码/输入挂载、输出目录、CPU/内存/磁盘限制、网络策略、日志、超时与取消。
- [ ] 定义 Maven/Java 构建插件 MVP 输入输出：公开 GitHub 仓库、分支或提交、构建命令、受控镜像和构建产物；定义 Maven 测试插件的报告收集与失败语义。
- [ ] 定义 Kubernetes 部署插件 MVP 输入：已授权且健康的 Kubernetes 环境、允许命名空间、受控 YAML 清单描述、镜像版本和部署策略；明确 MVP 不支持 Helm。
- [ ] 定义插件执行结果：状态、结构化输出、错误分类、日志引用、产物引用、可重试性。
- [ ] 定义插件安全边界：禁止任意镜像、特权容器、Docker Socket、任意宿主机挂载、未授权集群访问和凭据明文注入；日志、错误响应与 LLM 上下文必须脱敏。

### 验收结果

流水线只按插件描述符执行；进程内插件和 Docker 插件均可被统一调度、取消、记录日志和返回产物。

## 6. 产物模块

### 目标

管理插件产生的可下载或可供后续步骤使用的文件与结果。

### TODO

- [ ] 定义产物类别：构建包、测试报告、扫描报告、Kubernetes 清单快照、部署结果文件、日志归档。
- [ ] 定义产物发布、查询、下载、删除、上传失败、校验和不一致、存储不可用、过期和保留策略。
- [ ] 定义产物元信息：名称、类型、大小、校验和、来源运行/步骤、生成时间、存储位置和对应流水线/插件版本。
- [ ] 定义产物访问权限，至少继承项目读取权限；敏感产物可增加更严格策略。
- [ ] 定义后续步骤引用前序产物的语法和校验规则。

### 验收结果

## 7. Codex MCP 与智能分析模块

### 目标

向 Codex 提供受限工具，让自然语言请求变成平台内的受控操作；对失败运行提供已脱敏的诊断上下文。

### TODO

- [ ] 定义 Codex 登录/身份传递方式以及未登录响应。
- [ ] 定义 MCP 工具清单、每个工具的输入、输出、授权规则和幂等行为。
- [ ] 定义面向流水线的 MCP 工具：查询可用项目/仓库/环境、校验流水线草案、创建运行、查询运行、查询日志和获取失败分析上下文；MCP 只调用平台 REST/服务契约，不直接操作 Docker、Git 或 Kubernetes。
- [ ] 定义“缺少项目、环境、分支或配置”时的结构化追问响应，禁止模型自行推测。
- [ ] 定义流水线草案生成、校验、用户确认和触发之间的状态流转。
- [ ] 定义失败分析输入的脱敏边界、事实证据格式、模型推断标记和建议动作。
- [ ] 定义所有 MCP 调用的限流和错误映射。

### 验收结果

Codex 只能看到并操作当前用户已授权的资源；自然语言部署在配置缺失或确认不足时不会执行。

## 8. 流水线交付工作包

以下工作包只描述流水线 MVP 的交付顺序与完成边界；每个工作包开始编码前，仍须在 `.specify/pipeline/` 中完成相应的功能规格、验收场景与待澄清问题。

| 工作包 | 交付目标 | 依赖 | 完成标准 |
| --- | --- | --- | --- |
| WP-PL-01：流水线定义规格 | 确认 YAML v1、版本规则、校验规则、权限预校验和错误格式。 | 已完成的 IAM、项目、仓库、环境能力。 | `spec.md`、用户故事、验收场景和需求检查清单完成；所有会影响实现的产品歧义均已确认或明确延期。 |
| WP-PL-02：定义与校验 | 用户可以创建、修改、校验、启停和查询版本化流水线。 | WP-PL-01。 | 合法 YAML 生成不可变版本；非法 YAML 在执行前被拒绝并可定位；版本、项目与预配置资源隔离成立。 |
| WP-PL-03：运行记录与查询 | 用户可以基于已启用版本创建运行，并查询运行、阶段、步骤和日志。 | WP-PL-02。 | 每个运行绑定流水线和配置快照；运行状态可从创建追溯到终态；权限、幂等和跨项目隔离均可验证。 |
| WP-PL-04：调度与取消 | 平台可按依赖调度步骤，处理失败、超时、取消、重试和服务中断恢复。 | WP-PL-03。 | 不会执行失败依赖之后的步骤；取消与超时有确定终态；重复调度与恢复不会造成重复执行。 |
| WP-PL-05：插件框架 | 流水线可按固定版本调用受控的进程内或 Docker 插件。 | WP-PL-04。 | 插件输入、输出、日志、错误、超时和取消契约统一；停用或未知插件不能用于新运行。 |
| WP-PL-06：Maven 构建、测试与产物 | 在受控 Docker 容器中执行 Maven 构建/测试，并保存构建包和测试报告。 | WP-PL-05；产物存储决策。 | 不使用特权容器、Docker Socket 或任意宿主挂载；产物可追溯、可按权限查询；失败信息已脱敏。 |
| WP-PL-07：Kubernetes 部署 | 在已授权、健康的 Kubernetes 环境向允许命名空间执行受控部署。 | WP-PL-05、WP-PL-06；部署描述格式决策。 | 仅使用环境凭据引用；命名空间和环境权限均通过校验；部署结果可关联到运行与步骤。 |
| WP-PL-08：MCP 与失败分析 | Codex 可查询上下文、校验草案、创建/查询运行，并获取失败分析上下文。 | WP-PL-03；WP-PL-06 或 WP-PL-07 提供实际运行数据。 | MCP 只暴露当前用户有权限的数据和动作；缺失信息返回结构化追问；分析内容区分事实与推断。 |

### WP-PL-01 必须先确认的产品决策

- [ ] YAML 是否允许一个流水线包含多个仓库；MVP 建议：一个流水线只引用一个项目内公开 GitHub 仓库。
- [ ] YAML 中环境引用的形式：固定环境、运行时必填参数，或两者都支持；MVP 建议：允许声明为运行时必填参数，但实际值必须是当前项目已配置环境。
- [ ] 默认分支规则：运行未传入分支或提交时，是否使用仓库默认分支；MVP 建议：允许显式配置默认值，否则拒绝执行并要求用户补充。
- [ ] MVP 是否支持步骤并行；MVP 建议：先仅支持串行阶段和显式依赖，后续再增加并行。
- [ ] 重试范围与次数：仅允许人工重试整个运行，还是支持单步骤自动重试；MVP 建议：先支持人工基于原始快照重试，不启用自动重试。
- [ ] YAML 部署描述的来源：仓库内受控 Kubernetes 清单路径，还是运行请求传入内容；MVP 建议：只允许仓库内清单路径，禁止请求直接提交部署清单。
- [ ] 产物存储方式、容量上限与保留期；MVP 建议：先使用本地受控存储并设定按运行可追溯的短期保留策略，正式部署前再切换对象存储。

## 9. 推荐实施顺序

1. 租户用户与统一授权能力。
2. 项目、公开 GitHub 仓库、凭据引用与项目环境预配置。
3. 流水线 YAML 规范、校验和版本化。
4. 运行状态机、触发、查询、取消和日志。
5. 插件框架与进程内人工卡点插件。
6. Docker Maven 构建/测试插件与产物管理。
7. Kubernetes 部署插件与环境确认策略。
8. Codex MCP 工具与失败分析。

每一项进入实现前，都应在对应功能规格中补齐用户故事、验收场景和边界条件。
